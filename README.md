# Blackmagic Intensity Extreme Revival

**Current engineering decision — original hardware first, Ubuntu execution (24 October 2026).** Preserve the *actual* silver 2011 Mac mini / Thunderbolt / Comdis dock / Intensity Extreme (PCI **0xBDBD:0xA124**) as physical evidence. Build the **PCIe/firmware/register/DMA interface** on our existing **Ubuntu 24.04 Intel Mac mini**, using **strictly synthetic, evidence-limited register replay** while its Thunderbolt link is not connected. Native video/scratching simulation remains a downstream consumer test; it must never stand in for hardware. **No Sierra upgrade, recovery boot, driver swap or firmware change is required for this Ubuntu software lane.** The current Ubuntu host has two Thunderbolt 3 domains but **does not yet enumerate A124**. [Source-owned Ubuntu hardware-fidelity contract and witnessed acceptance](docs/a124-hardware-fidelity-ubuntu.md) · [Read-only Linux endpoint probe](hardware/ubuntu/a124_pci_port.py) · [44-case Ubuntu hardware interface acceptance](scripts/verify-a124-ubuntu-contract.sh).

**Software repair is hardware sustainability.**

A video-capture device does not stop being useful simply because its manufacturer stops supporting the software around it. This independent Fountain Coach project investigates whether a legacy **Blackmagic Intensity Extreme** can be brought back into service with documented diagnostics, reproducible reverse engineering, and eventually an openly implemented hardware interface.

Inspired by the practical spirit of a *Repair Café*: understand what is broken, share what we learn, and make functioning equipment useful for longer.

> **Current status — native capture/playback APIs recovered; HDMI receiver not locked.** Our self-authored programs enumerate the device, negotiate input and output modes, and submit a generated playback frame through the installed legacy driver. Earlier capture tests with external HDMI sources reported **no input signal lock** at 1080p30 and no valid frames; a temporary 720p60 test also failed. On 23 October, a new bounded 1080p30 test received **83 video callbacks, but every frame was explicitly flagged as having no input source** (zero valid frames, signal lock false). Source signal presence during this retest was not independently verified; missing lock is not by itself proof of failed receiver hardware. With Blackmagic HDMI OUT physically looped into HDMI IN, native tests established **half-duplex behavior**: whichever capture/playback mode was enabled second was rejected. Physical signal transfer and an independent replacement driver remain unverified.

**Latest fixed-wiring HDMI evidence (24 October 2026):** Silver Mac HDMI OUT → Intensity Extreme HDMI IN, with Intensity HDMI OUT disconnected, restores direct BMD HDMI EDID and the selected 1080p30 display mode. But two separate source-owned probes now measure the actual **macOS display timing at approximately 29.8907 Hz**, not 30 or 29.97: I/O Registry pixel clock 73,979,530 Hz / 2,475,000 pixels, and a separate CoreVideo display-link sample (120 timestamp-only callbacks, three physical runs). The Blackmagic receiver still reports **no input lock** when armed at 1080p30 without streaming. This measured *display-scheduler* discrepancy is a new actionable hypothesis, **not an electrical HDMI wire measurement or a proven root cause**. Do not change HDMI wiring, install drivers, modify display modes, or re-enable the old vendor capture stream as part of automatic tests. [Full live test and evidence](tests/2026-10-24-source-cadence-receiver-no-lock.md) · [read-only clock mapping tool](tools/sierra/hdmi-output-clock-witness.py) · [passive display-link cadence probe](tools/sierra/hdmi-displaylink-clock-witness.c).

**DeckLink 10.4 receiver acceptance corrected (24 October 2026):** The physical original Intensity Extreme reports **BMDDeckLinkSupportsInputFormatDetection = false** through a read-only vendor attributes call. Therefore detected-video-mode retrieval (`dvim`) is **not a valid required witness** on this model: the earlier status probe incorrectly required both `visl` signal lock and detected mode to declare a candidate. The [revised, capability-aware no-stream probe](src/decklink-input-lock-probe.cpp) uses only the real input-lock flag, labels the optional detected mode as not applicable, and separates **NO_LOCK**, **STATUS_UNKNOWN**, and **LOCK_CANDIDATE (not real frame acceptance)**. Its [8 classifier tests](tests/decklink_signal_lock_contract_test.cpp) passed on Sierra, modern macOS and Ubuntu. The exact physical **1080p30 test still reports 0/8 locked** (all status calls succeeded), while leaving BMD HDMI 1080p30 and cyuv=automatic unchanged. Original 10.4 frame-lifetime crash guard remains enabled, so no streams were started. [Capability and real signal-lock evidence](tests/2026-10-24-decklink-10-4-format-detection-and-lock-witness.md). **D4 remains OPEN.**

**IOGraphics 515.x root-cause and prevention (24 October 2026):** The actual Sierra host has **IOGraphicsFamily 515.4**, and the nearest published Apple [IOGraphics 515.3 source](https://github.com/apple-oss-distributions/IOGraphics/blob/IOGraphics-515.3/IOGraphicsFamily/IOFramebuffer.cpp) explicitly maps **nonautomatic cyuv connection-colour requests to RGB**, whereas automatic selection prefers YCbCr444. That exactly explains the physical cyuv=422 request returning API success but cmod=RGB (not YCbCr422). It is **not proof Intel HD3000 cannot generate 422 through other paths**. The source also shows IOFBCurrentPixelClock derives from **driver timing information**, not a physical HDMI waveform measurement; the 73.97953 MHz value remains an unresolved *driver-reported* discrepancy versus requested 74.25 MHz, not a proven faulty output PLL. **The misleading 422 trial is now disabled in all four source-owned C/Python entrypoints** and the guarded versions were compiled/deployed on Sierra; requests fail closed before any colour write or capture call, while verified cyuv=automatic restoration is preserved. **11 retired-command tests and 9 source-contract tests passed on Sierra, modern macOS and Ubuntu** (no CI). [Root-cause analysis and installed acceptance](tests/2026-10-24-iographics-5153-hdmi-color-clock-root-cause.md). The next focus is DeckLink 10.4 receiver-status and actual frame-init lifecycle under existing crash protection; **physical capture is still not accepted**.

**Verified Sierra IOGraphics source behaviour and installed lockout (25 October 2026):** The silver Mac runs **IOGraphicsFamily 515.4**. Apple's closest published [IOGraphics-515.3 original source](https://github.com/apple-oss-distributions/IOGraphics/blob/IOGraphics-515.3/IOGraphicsFamily/IOFramebuffer.cpp) explicitly substitutes **RGB for every nonautomatic `cyuv` colour-mode request** in `IOFramebufferParameterHandler::doIntegerSet`; only automatic selection can choose YCbCr444 when enabled and supported. This explains why a physically accepted `cyuv=0x10` request selected **RGB (`cmod=0x1`)**, rather than YCbCr422. It does **not** prove the actual HDMI wire encoding or chip's inability to output 422 by other mechanisms. The same original source shows `IOFBCurrentPixelClock` is derived from **graphics-driver timing information**, not a physical TMDS clock sensor; the observed 73.97953 MHz must not be treated as a proven HDMI wire-frequency defect. Both source-owned 422 trial commands and both C setters are now **blocked before hardware access**; **9/9 fail-closed tests on Sierra, macOS and Ubuntu** and **four actual installed Sierra entrypoint refusal tests (exit 65)** passed. The correct `cyuv=automatic` restoration remained operational and live Sierra BMD HDMI 1080p30 and YCbCr444 were independently verified. No cabling, driver, firmware, output refresh or capture stream changed. [Provenance and acceptance](tests/2026-10-25-iographics-515-colour-and-clock-provenance.md) · [locked-out 422 tests](tests/test_hdmi_retired_422_guard.py). Physical receiver lock and real frame capture **remain OPEN**.

**Sierra HDMI colour-control witness (24 October 2026):** Read-only IOGraphics shows the active BMD source requests **74.25 MHz** for both 1080p30 and 720p60, but its framebuffer reports **73.97953 MHz**. On the actual Sierra Mac, the *selected* colour mode **cmod=0x100 (YCbCr444)** while the connection control **cyuv=0x10000000 (automatic)** and the supported mask includes YCbCr422. Early guarded writes to the **wrong read-only selection field cmod** returned generic I/O error. The corrected standard write to **cyuv=0x10 (request 422)** was **accepted**, but the graphics driver switched its selected colour to **RGB (cmod=0x1)**, **not** YCbCr422, so no 422 receiver-lock test could be claimed. This exposed an **actual local+external watchdog restoration defect** (initially only 422/444 accepted), which was repaired; a separate real restore returned **cyuv=auto and cmod=YCbCr444** successfully. **Five synthetic RGB-restore regression tests pass on Sierra, macOS and Ubuntu**, but no crash-injected physical auto-restore has been proven. The last live inspection confirms the BMD source at **1080p30**, original 10.4 drivers and no watchdog processes. **No genuine HDMI input lock or capture.** [Physical incident and exact result](tests/2026-10-24-hdmi-cyuv-rgb-fallback-and-restoration-incident.md) · [repaired connection control](src/sierra-hdmi-connection-color-control.c) · [read-only timing and colour audit](tools/sierra/hdmi-timing-color-audit.py).

**Physical 720p60 outcome (24 October 2026):** The owner's hypothesis that 60 Hz may be the passing frequency was **tested on the actual fixed silver-Mac-to-Intensity HDMI connection**. Original DeckLink enumerated **720p60** as a supported INPUT mode (the original model does not capture 1080p60), and the silver Mac's BMD display successfully switched to **1280×720 @ UI 60 Hz**, under a separately running Sierra restore watchdog plus delayed SSH fallback on the modern Mac. The source's I/O Registry again published the same **73,979,530 Hz** pixel clock, now over 1,237,500 pixels/frame = **59.781438 Hz** source-side cadence (not independently measured HDMI wire clock). The source-gated original Blackmagic 10.4 input-status probe enabled 720p60 but returned **0/8 receiver-lock readings and no detected mode**; no frame streams were started. The controller, independent local watchdog, and delayed external SSH fallback all verified **restoration to BMD HDMI 1080p30**. **720p60 does not currently recover capture**, and D4 remains OPEN. [Physical 60 Hz evidence and restored-state record](tests/2026-10-24-hdmi-720p60-physical-no-lock.md) · [machine-readable fixture](fixtures/silver-hdmi-720p60-no-lock-2026-10-24.json) · [bounded 60 Hz trial implementation](tools/sierra/hdmi-720p60-bounded-trial.py).

## What we want to repair

The tested setup includes:
- **Blackmagic Intensity Extreme**, PCI vendor **0xBDBD**, device **0xA124**.
- **Comdis/i-tec THUNDERDOCK2** between the capture device and host.
- **2011 Mac mini**, macOS **10.12.6 Sierra**, with **Desktop Video 10.4** installed.

The device enumerates over Thunderbolt and PCI Express. macOS attaches the Blackmagic driver, including audio-related components. **Our independently written native test can now enumerate the device, discover video formats, and temporarily enable/disable input and output modes.** Following the verified CoreMediaIO isolation, Media Express now launches its interface and acquires a device resource (busy state `0x2`, returning to `0x0` when closed); actual captured frames remain unverified. [Repeatable regression results](tests/2026-10-21-post-isolation-driver-regression.md) distinguish those facts.

## The repair approach

1. **Observe before changing anything.** Record model IDs, software versions, connection topology, failures, and exact artifact hashes.
2. **Understand the working boundaries.** Separate PCI enumeration, driver attachment, firmware readiness, device usability, video DMA, and actual capture.
3. **Reconstruct behavior from evidence.** Analyze an authorized local copy of the legacy kernel extension using [Reverse Engineer Anything (REA)](https://github.com/morluto/rea) and [Ghidra](https://github.com/NationalSecurityAgency/ghidra).
4. **Implement a minimal diagnostic.** First determine whether a supported user client can report device, firmware and readiness state without modifying hardware.
5. **Reclaim the useful interface.** Build a portable video instrument with replaceable host backends. Examine independent driver implementation as a separate, testable objective.
6. **Measure what works.** Reproduce successful frames, timestamps, audio synchronization, and controlled output—rather than promising compatibility by assertion.

**No Syphon dependency.** The forward architecture is intended for current macOS, Linux, and iPadOS consumers, although a low-level Thunderbolt/PCI host is still needed for this particular device.

## Model-specific status decoder — 24 October 2026

We independently resolved the formerly indirect HDExtreme I/O Kit vtable calls using a [compile-only ABI verifier](driver/sierra/passive/verify-abi-layout.sh) on **the physical Sierra Mac mini**. The dispatch offsets `0x908` and `0x118` resolve to `IOPCIDevice::mapDeviceMemoryWithRegister` and `IOMemoryMap::getVirtualAddress`. The HDExtreme static initialization path maps BAR0 (register `0x10`), and its format detector points to a status candidate at **BAR0+`0x40`**. A separate [hash-pinned Mach-O virtual dispatch inspector](scripts/inspect_private_status_dispatch.py) verifies the HDExtreme `0x7a0` method slot resolves to inherited `HDProPCIExpress::ReadRegisterEndian` without publishing original binary bytes. The original code's `0xffffffff` invalid-response guard was identified.

Our [pure status classifier](src/intensity-input-status.c) and [11 synthetic C tests](tests/test-intensity-input-status.c) compiled and passed on both Sierra and Ubuntu. Twelve synthetic tests also pass across the two private-binary dispatch inspectors on Ubuntu. The separate [A124 firmware gate model](src/intensity-firmware-gate.c) passes six additional synthetic tests on both machines, and the hash-pinned private inspector now verifies the model's expected firmware-version byte **`0x0B`**. Model-specific static analysis traces its firmware version query to **BAR0+`0x224`**, while input status remains at **BAR0+`0x40`**; neither register has been read by our code. These are independent software test results, **not live BAR accesses, firmware readiness, signal lock, or captured video**. Read the exact [A124 status call-chain and evidence limits](docs/a124-input-status-call-chain-2026-10-24.md).

The [recovery inventory](tests/2026-10-24-sierra-recovery-inventory.md) found no configured Time Machine destination or verified alternative boot environment, and the `Fresh` volume contains existing user data. An actual PCI-driver takeover must remain blocked until a separate, tested rollback boot exists.

## Fountain Video — native Sierra application (24 October 2026)

**Fountain Video.app has been built and launched on the real 2011 Intel Mac mini.** This is a native AppKit application, rather than another Python-only video simulation or command-line diagnostic. It is installed in the Sierra account's personal Applications folder and communicates directly with the existing Desktop Video 10.4 runtime, bypassing the isolated crash-prone CoreMediaIO plug-in.

Real HDMI preview and recording paths exist but are not yet accepted against genuine frame data. [Source, build instructions, and test results](apps/fountain-video-sierra/README.md).

## Why this matters

Keeping functional equipment in use may reduce electronic waste and the embodied impacts of purchasing replacement devices. But *carbon savings are not assumed*. An old computer also consumes power, and reverse-engineering activity has a cost. Our [sustainability ledger](docs/sustainability.md) explains which data would justify a real claim.

We want this to be both an engineering project **and a practical public example of software-led repair**—a place where a repair volunteer, artist, researcher or systems architect can follow the evidence and try the next experiment.
